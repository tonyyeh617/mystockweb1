ask:
fetch_volume_history.py使用者點網頁即會觸發嗎?

ans:
不會。fetch_volume_history.py 是獨立的 Django management command，只能用
手動執行，網頁操作不會觸發它。
對應的「推薦選股」頁面（views.py:97 view）只呼叫 find_vwap_oscillation_candidates()（finmind.py:284），而這個函式只是讀取資料庫裡已經抓好的 stock.prices，完全不會呼叫 FinMind API，也沒有呼叫 plan_volume_fetch / fetch_price_range（這兩個是 fetch_volume_history.py 指令才會用到的函式）。
所以流程是：
你手動跑 python manage.py fetch_volume_history（會呼叫 API 把近3年成交量資料存進 DB，且支援中斷續跑）。
使用者點網頁「推薦選股」按鈕時，只是從 DB 讀取已存好的資料做篩選計算，不會觸發任何 API 請求。

ask:
fetch_dividends.py執行後，再執行會接續還是會重來?

ans:
看情況，分兩種結果：

遇到 API 流量限制中途失敗：會把目前處理到的 last_stock_id 記錄進 FetchCheckpoint（key=dividend_history）並停止。下次執行會自動接續，從 stock_id__gt=last_stock_id 繼續抓（fetch_dividends.py:42-46）。

順利跑完整份股票清單（沒有中途失敗）：最後會把 checkpoint.last_stock_id 重設為空字串（fetch_dividends.py:79-81），所以下次執行會從頭掃描全部股票。不過因為每檔股票若已有資料會直接「略過（已有資料）」不呼叫 API（fetch_dividends.py:56-62），所以實際上不會重新下載已抓過的資料，只是會重新走一遍清單、很快跳過。

另外兩個參數會影響這個行為：

--reset：手動強制忽略進度，從頭開始（即使上次沒跑完）。
--force：即使已有資料也會重新呼叫 API 覆蓋更新（用於更新最新年度股利公告），這時才是真正「重來」地重抓每一檔。

ask:
fetch_all_prices.py、fetch_volume_history.py、fetch_dividends.py 讀取資料庫的內容是同一個還是分開?

ans:
都是同一個 SQLite 資料庫（db.sqlite3），但寫入的資料表（model）分兩類：

指令	寫入的資料表	說明
fetch_all_prices	DailyPrice（透過 ensure_prices）	每日股價
fetch_volume_history	同一個 DailyPrice（透過 fetch_price_range）	近3年成交量歷史，其實是補同一張股價表的區間資料
fetch_dividends	Dividend（透過 ensure_dividends）	股利政策，獨立的表，跟股價完全分開
也就是說：

fetch_all_prices.py 和 fetch_volume_history.py 其實是同一張表 DailyPrice，只是抓取的日期區間和觸發邏輯不同（前者抓「最新未抓過」的資料，後者抓「近3年指定區間」），兩者會互相補齊/覆蓋同一檔股票的同一天資料（finmind.py:62 和 finmind.py:125 都是 DailyPrice(...)，並用 unique_fields=["stock","date"] 做 upsert，不會重複）。
fetch_dividends.py 寫入的是獨立的 Dividend 表，跟股價表完全無關。
三者共用的另一張表是 FetchCheckpoint（記錄進度用），但靠不同的 key 區分，彼此互不干擾：

fetch_volume_history 用 key="volume_history"（整體進度）以及每檔股票一筆 key="volume_covered:<股票代號>"（finmind.py）。
fetch_dividends 用 key="dividend_history"（fetch_dividends.py）。
所有指令也都共用同一張 Stock 表（股票清單），透過 ForeignKey 關聯。

ask:
若放到同一個，會不會只要固定執行一個檔即可

ans:
技術上現在這套常數下兩者確實有重疊，但不建議只留一個，原因如下：

它們雖然寫入同一張 DailyPrice 表，但抓取邏輯的方向不同：

fetch_all_prices.py（透過 finmind.py:43）：
只在該股票「完全沒有任何價格紀錄」時，才會一次回補 YEARS(5年) + WARMUP_DAYS(120天) 的歷史（finmind.py:50-51）。
之後只會「從最後一筆之後往前補到今天」，不會再往回補更早的資料。

fetch_volume_history.py（透過 finmind.py:158 + fetch_price_range）：
明確檢查資料庫現有資料是否真的涵蓋篩選股票要用的近3年區間（finmind.py:169-178），不夠的話才主動回補那段區間，並記錄 volume_covered:<股票代號> 標記避免重複驗證。
目前常數下（5年回補 > 3年需求），只要 fetch_all_prices 有機會對每一檔股票完成「第一次」抓取，它留下的歷史其實已經足夠讓 finmind.py:284 直接從資料庫判斷涵蓋度（這函式本身也會再檢查一次 rows[0]／rows[-1] 是否在區間內，見 finmind.py:300-302），所以理論上合併成只跑 fetch_all_prices 也可能湊巧夠用。

但不建議這樣做，因為：

fetch_all_prices 一次只處理 300 檔（--limit 300），且一旦某股已經 last_fetched，之後永遠不會再往回補——如果未來把 YEARS／WARMUP_DAYS 調小、或某股第一次抓取時剛好 API 回傳不完整，就會永久留下涵蓋不足的洞，而且沒有任何機制會發現或修補它。
fetch_volume_history 正是為了「獨立驗證＋按需回補」這個保證而存在，不依賴 fetch_all_prices 內部的隱性假設，兩者耦合在一起會讓股息/選股功能的資料正確性變成要去理解另一支指令的副作用才能保證，維護成本更高。
簡單說：目前可能剛好夠用，但這是巧合而非設計保證，兩支指令各自負責不同的資料保證（「盡量每日更新到最新」vs「保證篩選所需的歷史區間涵蓋度」），建議維持分開執行。

ask:
fetch_dividends呢?

ans:
fetch_dividends.py 不應該合併，而且性質完全不同，無法互相取代：

不同資料表、不同 FinMind dataset：寫入的是獨立的 Dividend 表，資料來源是 TaiwanStockDividend（股利政策表），跟 fetch_all_prices／fetch_volume_history 用的 TaiwanStockPrice 完全是兩個不同的 API 端點，彼此沒有資料重疊，合併沒有意義。

抓取方式也跟股價邏輯不一樣——不是「每日增量補最新」，而是「一次抓全部歷史、之後整段跳過」：

finmind.py:313-315：只要 stock.dividends.exists() 就直接 return，不像 ensure_prices 會每天自動補最新。
想要抓到「今年新公告的股利」，只能用 --force（或網頁上的「↻ 更新股息資料」按鈕），而且 force=True 時是整段 2005 年至今重抓一次，不是增量補差異——跟 ensure_prices 的增量設計完全不同，所以更不適合直接套用 fetch_all_prices 那種「每小時排程、增量補最新」的用法。
結論：fetch_dividends 必須維持獨立指令。如果之後想讓股息資料也能定期自動更新最新年度，需要另外排程執行 fetch_dividends --force（但要注意這是整段重抓、較耗 API 次數，不建議像 fetch_all_prices 那樣頻繁排程，一年跑個幾次抓新公告的股利即可）。

ask:
每一小時我只能抓三百筆，要怎麼排比較好?

ans:
關鍵問題：這三支指令都是呼叫同一個 _get()（同一個 FinMind endpoint），共用同一個「每小時 300 次」的額度，不是各自獨立的 300 次。所以排程時最重要的原則是：同一小時內盡量只讓一支指令在用額度，避免互相搶額度。

建議排法
原則：依「初期建檔」跟「平常維運」分兩階段處理

階段一：初期建檔（fetch_volume_history、fetch_dividends 第一次跑時）
這兩個第一次執行要掃過全部股票、灌進初始資料，會大量消耗額度，建議：

先把 fetch_all_prices 的排程暫停（工作排程器右鍵「停用」即可），
手動連續執行 fetch_volume_history（之後 fetch_dividends），讓它們各自獨佔 300 次/小時，每次碰到額度上限就自動停並記錄進度（checkpoint），等一小時後再執行一次即可接續，直到看到「全部股票皆已處理完成」。
建完之後再把 fetch_all_prices 排程重新啟用。
這階段因為兩者互斥（不會同時搶），不需要特別分配額度。

階段二：平常維運（建檔完成後）
建檔完成後，fetch_volume_history 和 fetch_dividends（不加 --force）對已有資料的股票會直接略過、不耗用額度（見你選取的 fetch_dividends.py:56-61），只有新上市股票才會真的呼叫 API，次數很少。這時排程建議：

指令	建議時段	理由
fetch_all_prices	每小時（不變）	主力任務，收盤後連跑幾小時即可補完全部股票
